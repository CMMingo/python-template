You've been handed a spec (usually just-written, `docs/specs/<type>-<yyyy_mm>-<name>/SPEC.md`, on its own branch) and asked to actually build it: one continuous run of implementation, checks, and review that keeps going seam by seam until the whole spec is done -- not a single step that stops and waits.

## Process

1. Read the spec's *Implementation Decisions* and *Testing Decisions* sections, and the task breakdown in the sibling `plan/PLAN.md`. The seam(s) and tasks are already agreed there -- don't re-derive them, and don't second-guess a decision the spec or plan already settled.
2. Loop through the seams named in *Testing Decisions*, in order, until every one is covered:
   - Implement via the `tdd` skill: red (failing test), then code. Before running the seam's test to confirm green, dispatch the `logic-checker` subagent against the seam's diff and the spec's *Implementation Decisions* for it -- it checks whether the code actually does what was asked, since a test only catches what it was written to catch, not what's missing entirely. Fix anything real it flags, then confirm green.
   - Check off the task(s) this seam's work completed in `plan/PLAN.md`. If what you learned while building this seam changes the plan -- a task turned out unnecessary, a new one is needed, a seam needs splitting -- update `PLAN.md` to match reality and say why, rather than letting it drift stale.
   - Report briefly in the conversation (what changed, what `logic-checker` flagged if anything, test status), then continue immediately into the next seam. This report is for visibility, not a checkpoint -- don't wait for a reply before moving on.
3. Run checks regularly as you go, not only at the end: `make test` (or `make test-fast` mid-loop), `make lint`, and `make typecheck`. Don't let failures pile up across multiple seams before addressing them.
4. Once every seam in *Testing Decisions* is covered and the full suite passes, do a deliberate refactor pass over whatever `tdd`'s loop flagged as a larger opportunity (duplication across seams, a naming inconsistency, structure that only makes sense once you can see the whole feature) -- then re-run the full suite to confirm nothing broke. Skip this step if nothing of that kind was flagged; it's not busywork for its own sake.
5. Dispatch the `code-reviewer` subagent for an independent pass over the resulting diff.
6. If `code-reviewer` finds something real, fix it and re-run the full suite before considering the work done.
7. Write a report to `docs/specs/<type>-<yyyy_mm>-<name>/reports/NNNN-implement.md` (create `reports/` if this is the first run against this spec; number after whatever's already there -- see the `spec` skill's "Where things live" section for the convention). Cover: what was implemented per seam, anything `logic-checker`/`code-reviewer` flagged and how it was resolved, any assumptions made and why, final test/lint/typecheck status, and anything left for later. Write it for someone with zero context on this conversation.
8. Stop there. Report in the conversation what was implemented, that tests pass, and that it's been reviewed -- then say it's ready for `/commit-push`. Don't commit or push yourself; that's a deliberate, separately-triggered step.

## Rules

- **Keep going on your own.** Step 2's loop doesn't pause between seams waiting for a go-ahead -- it reports and continues, whether this is a live session someone's watching or a `claude-handoff` run nobody's watching. The reports exist for visibility, not to gate progress. The only things that stop the loop early are a genuine blocking ambiguity (below) or a test failure that needs `diagnosing-bugs`.
- **Keep `plan/PLAN.md` and `reports/` current as you go**, not just at the end (steps 2 and 7). If this run gets interrupted for any reason before every seam is done -- context limit, the user stopping it, anything -- whoever resumes should be able to read `PLAN.md`'s checkboxes and the latest report and know exactly where things stand, without re-deriving it from the diff. Resuming is then just re-invoking `implement` against the same spec.
- If you hit a genuine ambiguity the spec didn't resolve, don't guess silently, and don't stop and wait by default either: make the best-supported call, implement it, and flag it plainly in your report as an assumption -- the same convention `/spec` itself uses when a question goes unanswered after three rounds. Only stop and ask if the ambiguity is one no reasonable assumption could recover from (it changes *what's* being built, not just *how*).
- Don't expand scope beyond what the spec's *Implementation Decisions* actually named. If you notice something the spec should have covered but didn't, flag it in the report rather than deciding it yourself.
- This skill assumes a branch already exists for the work (created by `/spec`). If there isn't one, create it first, named consistently with the spec's slug.
- If a test fails for a reason that isn't immediately obvious -- the cause doesn't jump out after a quick look, or your first fix attempt didn't produce the expected result -- don't keep guessing inside this loop, whether the confusing behaviour is in code you just wrote or in something pre-existing your change exposed. Call the Skill tool with `diagnosing-bugs`, passing it this spec's path and the exact failure, and wait for its report. Resume the `tdd` loop from where you left off once it hands back a diagnosis and fix. Feature work and debugging are deliberately different processes here -- don't blur them by debugging ad hoc in this loop.
