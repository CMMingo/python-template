You've been handed a spec (usually just-written, `docs/specs/<type>_<name>/SPEC.md`, on its own branch) and asked to actually build it: one continuous run of implementation, checks, and review that keeps going seam by seam until the whole spec is done -- not a single step that stops and waits.

## Before you start

Check the branch: `git branch --show-current`. If it is `main`, `master`, `dev` or `develop` (or HEAD is detached), don't start building. Ask the user to confirm creating a dedicated branch -- propose `<type>/<name>` from the spec folder name, for example `feat/multi-edit` for `docs/specs/feat_multi-edit/` -- and wait for the answer; once confirmed, create it and check it out. In an unattended `claude-handoff` run, where nobody can answer, create that branch yourself and say so in `REPORT.md`. If you are already on a dedicated branch for this work, carry on.

## Process

1. Read the spec's *Implementation Decisions* and *Testing Decisions* sections, and the task breakdown in the sibling `PLAN.md`. The seam(s) and tasks are already agreed there -- don't re-derive them, and don't second-guess a decision the spec or plan already settled.
2. Loop through the seams named in *Testing Decisions*, in order, until every one is covered:
   - Implement via the `tdd` skill: red (failing test), then code. If the spec has three or more seams, then before running a seam's test to confirm green, dispatch `code-reviewer` in spec mode for that seam (pass it the spec path and the seam) -- it checks whether the code actually does what was asked, since a test only catches what it was written to catch, not what's missing entirely. Fix anything real it flags, then confirm green. With fewer seams, skip this per-seam check: the full review in step 5 covers the spec.
   - Check off the task(s) this seam's work completed in `PLAN.md`. If what you learned while building this seam changes the plan -- a task turned out unnecessary, a new one is needed, a seam needs splitting -- update `PLAN.md` to match reality and say why, rather than letting it drift stale.
   - Report briefly in the conversation (what changed, what the seam review flagged if anything, test status), then continue immediately into the next seam. This report is for visibility, not a checkpoint -- don't wait for a reply before moving on.
3. Run checks regularly as you go, not only at the end: `just test` (or `just test-fast` mid-loop), `just lint`, and `just typecheck`. Don't let failures pile up across multiple seams before addressing them.
4. Once every seam in *Testing Decisions* is covered and the full suite passes, do a deliberate refactor pass over whatever `tdd`'s loop flagged as a larger opportunity (duplication across seams, a naming inconsistency, structure that only makes sense once you can see the whole feature), limited to code this change added or modified -- if you notice something in older code, mention it in the report instead of touching it -- then re-run the full suite to confirm nothing broke. Skip this step if nothing of that kind was flagged; it's not busywork for its own sake.
5. Dispatch the `code-reviewer` subagent for an independent pass over the resulting diff. Give it the spec path so it also checks the work against the spec's *Implementation Decisions* (intent and completeness), not only correctness.
6. If `code-reviewer` finds something real, fix it and re-run the full suite before considering the work done.
7. Write the report to `docs/specs/<type>_<name>/REPORT.md` (create it on the first run against this spec; on a later run, update it in place and add a dated section rather than creating another file -- see the `spec` skill's "Where things live" section). Cover: what was implemented per seam, anything `code-reviewer` flagged and how it was resolved, any assumptions made and why, final test/lint/typecheck status, and anything left for later. Write it for someone with zero context on this conversation.
8. Stop there. Report in the conversation what was implemented, that tests pass, and that it's been reviewed -- then say it's ready for `/commit`. Don't commit or push yourself; committing is a deliberate, separately-triggered step and pushing is the user's.

## Rules

- **Keep going on your own.** Step 2's loop doesn't pause between seams waiting for a go-ahead -- it reports and continues, whether this is a live session someone's watching or a `claude-handoff` run nobody's watching. The reports exist for visibility, not to gate progress. The only things that stop the loop early are a genuine blocking ambiguity (below) or a failure you must stop on instead of debugging (below).
- **Keep `PLAN.md` and `REPORT.md` current as you go**, not just at the end (steps 2 and 7). If this run gets interrupted for any reason before every seam is done -- context limit, the user stopping it, anything -- whoever resumes should be able to read `PLAN.md`'s checkboxes and `REPORT.md` and know exactly where things stand, without re-deriving it from the diff. Resuming is then just re-invoking `implement` against the same spec.
- If you hit a genuine ambiguity the spec didn't resolve, don't guess silently, and don't stop and wait by default either: make the best-supported call, implement it, and flag it plainly in your report as an assumption -- the same convention `/spec` itself uses when a question goes unanswered after three rounds. Only stop and ask if the ambiguity is one no reasonable assumption could recover from (it changes *what's* being built, not just *how*).
- Don't expand scope beyond what the spec's *Implementation Decisions* actually named. If you notice something the spec should have covered but didn't, flag it in the report rather than deciding it yourself.
- **Debugging code related to this spec is an option you have.** If a test fails for a reason that isn't immediately obvious -- the cause doesn't jump out after a quick look, or your first fix attempt didn't produce the expected result -- don't keep guessing inside this loop. When the failing code belongs to this spec (code this work added or modified, or something pre-existing that this change exposed within the spec's scope), dispatch the `debugger` subagent directly. Pass it the spec path, the seam you were on, the exact failure and what you already tried, and tell it to stay on the current branch (this work already has its own) and not to commit. It runs its own diagnosis loop, fixes the cause with a regression test where there is a correct seam, and writes its report to `docs/debug/<slug>.md`. Read its report back, note the diagnosis and the report path in `REPORT.md`, and resume the `tdd` loop from where you left off. Feature work and debugging stay separate processes: don't debug ad hoc in this loop, hand it to `debugger`.
  - **Stop instead of debugging** when the failure is outside this spec's scope (a bug in unrelated code), when the user told you not to debug, or when `debugger` hits its round cap and reports it is stuck. Give the user the exact failure, the spec path and the seam you were on, say the failure is a job for `/diagnosing-bugs` (a manual skill you cannot start yourself), and in an unattended `claude-handoff` run write it into `REPORT.md` and end the run there. Re-invoke `implement` against the same spec once it is resolved.
